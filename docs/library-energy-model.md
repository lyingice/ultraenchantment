# 附魔图书馆 · 能量模型设计（v4 提案）

> **状态**：设计已定稿，**尚未实现**。
> **来源**：2026-10 与作者的一轮逐项追问（grill），所有数值与维度均由作者拍板。
> **取代**：v3 的「按 `(谱系, 阶级)` 分池的点数」模型。

---

## 0. 为什么要改

v3 的图书馆把库存按 **`(谱系, 阶级)`** 分池（`LibraryKey(root, tier)`）。问题：

1. **30 条谱系 × 3 阶级 = 90 个桶** —— 玩家面对 90 个互不相通的池子
2. **存了没用** —— 图书馆没有出口，能量攒着不知道干什么
3. **NATIVE 阶花费为 0** —— 平衡漏洞，比灌注台还宽松
4. **图书馆的取出逻辑抄漏了神化的关键机制**（见 §7）

作者的新构想：**图书馆存抽象的「能量单位」，作为进阶台的燃料。**

---

## 1. 核心一句话

> **图书馆是电池，进阶台是用电器，书是燃料。**
>
> **图鉴管「你能取什么」，能量管「你能取多少」。**

---

## 2. 存储维度：8 类能量

**2 大家族 × 4 阶级，不区分谱系。**

```
                原生    高阶    超级    究极
阶级单位(进阶)   ——      5      10      20     ← 只有 3 档
等级单位(提级)   ?       ?       ?       ?     ← 4 档
```

**决策**：锋利存的和耐久存的进**同一个桶**。

**理由**：
- 「谱系」这一维已经由**图鉴**承担（图鉴记「你见过锋利·高阶」）
- 图书馆只负责能量经济，两者职责分开，各自都简单
- 90 个桶 → 8 个桶

**注意**：**阶级单位只有 3 档**（高阶/超级/究极）—— 没有「升到原生」这回事。等级单位有 4 档。

---

## 3. 家族归属

| 书 | 家族 | 定档依据 |
|---|---|---|
| 铭刻书（载体书） | **提级** | 书上的 `tier` |
| 升级书 | **提级** | 书上的 `tier` |
| 定向进阶书 | **进阶** | 书上的 `toTier` |
| 通用进阶书 | **进阶** | 书上的 `toTier` |

**作者的原话**：「铭刻书对标的是普通附魔书，而升级书其实是一种不分附魔种类的铭刻书，这两者是有关联的。」

**代码依据（两者同量纲）**：
- 升级书：`AnvilEvents:506-527` —— `spec.targetLevel()` 被**直接写进** `tierLevel`
- 铭刻书：`InscriptionLogic` —— `entries[].level` 也被**直接写进** `tierLevel`

⇒ 两个字段是同一个量，**共用同一个折算函数**。

---

## 4. 折算函数

```
f(level) = 2^(level - 1)
```

**沿用神化**（`EnchLibraryTile.levelToPoints:110`）。

| 等级 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| f | 1 | 2 | 4 | 8 | 16 | 32 |

⇒ **边际成本翻倍**，「两本 2 级 = 一本 3 级」自然成立。

---

## 5. 存入（书 → 能量）

**统一原则：越通用的书，存入产出越高。**
因为它对你越有用，放弃它的**机会成本**越大 —— 否则没人愿意把通用书存进去。

| 书 | 产出 |
|---|---|
| 铭刻书 `(tier, level)` | 等级单位·`tier` **+= f(level)** |
| 升级书 `(tier, targetLevel)` | 等级单位·`tier` **+= f(targetLevel) × 4** |
| 定向进阶书 `(toTier)` | 阶级单位·`toTier` **+= 升阶价**；等级单位·`toTier` **+= 1** |
| 通用进阶书 `(toTier)` | 阶级单位·`toTier` **+= 升阶价 × 4**；等级单位·`toTier` **+= 4** |

其中：

```
升阶价 = required_level × 阶级系数
阶级系数：高阶 ×1、超级 ×2、究极 ×4
```

**`required_level` 的实际取值**（见 §6）。

**通用加成 N = ×4**（作者的决策）。

**为什么进阶书也喂一点等级单位**：进阶书把 `tierLevel` 归 1，那「新阶级的第 1 级」有实际价值，所以给 `f(1) = 1`（通用版 ×4 = 4）。

---

## 6. 升阶价 = required_level × 阶级系数

### ⚠️ 一个必须知道的实情

**数据包里 `required_level` 从来没有被显式指定过。**

```
显式指定 required_level（三参 stage(...)）的行数: 0
```

全部走默认（`LineageTable:254` → `requiredLevel = null` → `UEStages:175` 取 `source.maxLevel()`）。

⇒ **每个谱系的三阶 `required_level` 是同一个值 = 该附魔的原版满级。**

| 谱系 | required_level | 高阶 | 超级 | 究极 |
|---|---|---|---|---|
| 锋利 | 5 | **5** | **10** | **20** |
| 耐久 | 3 | **3** | **6** | **12** |
| 经验修补 | 1 | **1** | **2** | **4** |

**⇒ 强附魔升阶更贵，弱附魔升阶更便宜。** 这是数据驱动的定价。

**为什么乘阶级系数**：光用 `required_level` 会让三阶同价，「究极」的重量被抹平。乘 ×1/×2/×4 补上递增，且**不动数据包**（改数据包会同时影响进阶门槛判定，面更大）。

---

## 7. 向上兑换：4 : 1

```
原生 ──4:1──> 高阶 ──4:1──> 超级 ──4:1──> 究极
```

**R = 4 是「有损耗」的**：阶级系数是 ×1/×2/×4，定价比是 2:1，而兑换率是 4:1 ⇒ **多付 100%**。

| R | 代价 | 是否损耗 |
|---|---|---|
| 2 | 与定价一致 | ❌ 无损（不能用） |
| **4** | 多付 100% | ✅ **采用** |
| 8 | 多付 300% | 太严厉 |

**兑换在哪发生**：图书馆界面上的一个按钮，**手动兑**。

---

## 8. 取出（能量 → 书）

两条门槛，职责不重叠：

| 门槛 | 管什么 | 依据 |
|---|---|---|
| **图鉴** | 你能取**什么**（哪些 `(谱系, 阶级)`） | 玩家附件 `CodexData` |
| **能量** | 你能取**多少**（等级多高） | 8 类计数器 |

**取出一本书的花费 = 它存入时的产出**（对称，1:1）。

**等级完全不受图鉴限制** —— 图鉴只解锁 `(谱系, 阶级)`，等级由能量管。

**⇒ 「见过的最高级」这个天花板删掉**（和神化不同），因为它和图鉴的职责重复，会让玩家算不清。

---

## 9. 进阶台：两个操作，两种单位

**作者的原话**：「进阶与升级是两个概念，附魔进阶台不应该只消耗经验，可以尝试让进阶附魔图书馆给它提供阶级单位和等级单位。」

| 操作 | 改什么 | 花什么 |
|---|---|---|
| **升阶** | `stageId`（跨阶级） | **阶级单位**·目标阶级 = `required_level × 系数` |
| **提级** | `tierLevel`（阶级内） | **等级单位**·该阶级 = `f(level) - f(existing)`（边际差） |

### 好消息：台子已经连上图书馆了

`AscensionTableMenu` 现状（**代价不是经验，是图书馆库存**）：

| 事实 | 位置 |
|---|---|
| 代价不是经验，是图书馆库存 | 类文档 `:54` |
| 用**原版附魔台的书架环**找「附近」的图书馆 | `:57`（`EnchantingTableBlock.BOOKSHELF_OFFSETS`） |
| 多座图书馆**池化**：校验看总量、扣减按顺序摊 | `:60` |
| 严格 **全量校验 → 扣库存 → 写物品** | `:461-484` |

**所以要改的只有两处**：
1. **库存的键**：`(谱系, 阶级)` → **`(家族, 阶级)`**
2. **花费拆成两笔**：升阶扣阶级单位、提级扣等级单位（现在是一次应用、一笔扣款）

## 10. 走一遍玩家的实际流程

| 步骤 | 图书馆状态 |
|---|---|
| 捡到「锋利 III」附魔书（铭刻书 高阶 L3）→ 存 | 等级单位·高阶 = **4** |
| 又存一本「耐久 II」 | 等级单位·高阶 = **4 + 2 = 6** |
| 图鉴自动解锁 `锋利·高阶`、`耐久·高阶` | — |
| 进阶台上把锋利从原生**升到高阶** | 阶级单位·高阶 **-= 5** |
| 进阶台上把锋利·高阶从 **1 级提到 3 级** | 等级单位·高阶 **-= (4 - 1) = 3** |
| 攒了 4 个「原生」等级单位 → 兑成 **1** 个「高阶」 | 等级单位·高阶 += 1 |

**关键**：整个过程中**谱系完全不参与计算**。锋利和耐久只是「取出来时选哪个」，不影响存进去值多少。

### ⚠️ 第 6 条：v3 抄漏了神化的关键机制

神化 `EnchLibraryContainer.onButtonClick:137`：

```java
int targetLevel = shift
    ? Math.min(getMax(ench), 1 + (int)(Math.log(points + levelToPoints(curLvl)) / Math.log(2)))
    : curLvl + 1;                                    // ← 普通点击就是 +1 级
```

**普通点击 = `curLvl + 1`。** 等级是在**输出槽那本书上，一级一级往上点**的 —— 不是「一次性选一个等级取出」。

**v3 完全丢了这条**：忽略输出槽已有等级、永远取「能付的最高级」或「1 级」，中间等级取不到。

## 12. 新需求：图鉴界面

**作者要求**：「图鉴最好能够打开，最好是进阶台和图书馆提供按钮作为玩家打开界面查询的入口。」

### 设计

- **一个只读界面**（不是容器菜单，没有槽位）
- 内容：所有 `(谱系, 阶级)` 组合，**已解锁 / 未解锁**两种状态
- 入口：**图书馆界面**和**进阶台界面**各有一个「图鉴」按钮
- 可顺带显示：该组合的升阶价、当前能量余额

### ⚠️ 技术障碍：图鉴数据现在不同步

`UEAttachments.CODEX` **刻意没有 `.sync()`**（见 `UEAttachments` 类文档）。

要渲染图鉴界面，**必须先把数据送到客户端**。两个选项：

| 方案 | 说明 |
|---|---|
| **A. 给附件加 `.sync()`** | NeoForge 自动同步给拥有者。最简单。代价：每次变化都会发包 |
| **B. 打开界面时按需发包** | 只在玩家点按钮时发一次。省流量，但要自己写包 |

**建议 A** —— 图鉴是「玩家自己的数据」，同步语义天然，而且数据量小（`Map<ResourceLocation,Integer>`，位掩码）。

## 15. 升阶条件与超限折算

### 15.1 升阶条件 = 该阶级的**数据包上限**满

**不是超限。** 理由见下。

### 15.2 🔴 硬约束：超限不能作为升阶的必要条件

**证据**：神化的超限来自**配置文件**，不是默认行为。

`ApothEnchEvents:301-323`：

```java
Configuration enchInfoConfig = new Configuration(ApothicAttributes.getConfigFile("enchantments"));
//                    ↑ 配置文件，不是数据包
EnchantmentInfo info = EnchantmentInfo.load(ench, enchInfoConfig);   // 每个附魔读一段
```

查询（`ApothicEnchanting:202`）：有配置就用，没有就 `EnchantmentInfo.fallback(ench)` = **原版上限**。

> **不改配置文件时，神化根本没有超限。**

⇒ **若把超限设为升阶条件，未配置超限的整合包里进阶会永久卡死。** 这是硬约束，不是偏好。

### 15.3 超限折算成新阶级的起始等级：**2 : 1**

```
升阶后起始等级 = 1 + floor(超限等级数 / 2)
超限等级数     = 当前 tierLevel - 该阶级的数据包 max_level
```

例（锋利，数据包上限 5）：

| 升阶前 | 超限等级数 | 升阶后 |
|---|---|---|
| 高阶 L5 | 0 | 超级 **L1** |
| 高阶 L6 | 1 | 超级 **L1** |
| 高阶 L7 | 2 | 超级 **L2** |
| 高阶 L8 | 3 | 超级 **L2** |
| 高阶 L10 | 5 | 超级 **L3** |

### 15.4 为什么这样设计

| | |
|---|---|
| ✅ **深耕不浪费** | 超限投入变成新阶级的启动资金，玩家敢投 |
| ✅ **升阶条件清晰** | 「基础段满」由数据包定义，不依赖配置 |
| ✅ **真选择** | 早升 = 快进新曲线；晚升 = 攒启动资金。两条路都有道理 |

### 15.5 数值验证（锋利：高阶 `3+1L` / 超级 `6+1.5L` / 究极 `10+2.5L`）

| 路线 | 落点数值 |
|---|---|
| 高阶 L5 直接升 | 超级 L1 = **7.5**（比高阶 L5 的 8 **还低** —— 升阶瞬间净亏） |
| 高阶 L8 再升 | 超级 L2 = **9** |
| 高阶 L10 再升 | 超级 L3 = **10.5** |
| 一直不升，高阶 L10 | **13** |

**⇒ 升阶永远是「短期亏、长期赚」。** 玩家要自己找交叉点 —— 这就是选择。

## 16. 一句话总结

> 书存进图书馆变成**两种能量**（阶级单位 / 等级单位），按**阶级**分档、**不分谱系**；
> 能量可以在**同类内 4:1 向上兑换**；
> **图鉴**决定你能取出哪些 `(谱系, 阶级)` 的书，**能量**决定你能取多高等级；
> **进阶台**用这两种能量驱动它的两个操作 —— **升阶花阶级单位、提级花等级单位**。
> **升阶条件 = 该阶级的数据包上限满**（不依赖神化配置）；**超限部分按 2:1 折算成新阶级的起始等级** ——
> 于是「早升阶 vs 先深耕」成为真选择，而不是惩罚。
