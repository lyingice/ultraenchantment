## 3. 载荷 schema

### 3.1 载体书（铭刻型）

组件 id：ultraenchantment:inscription_spec

    {
      "tier": "advanced",
      "entries": [
        { "enchantment": "minecraft:sharpness", "level": 3 },
        { "enchantment": "minecraft:looting",   "level": 2 }
      ]
    }

| 字段 | 类型 | 约束 |
|---|---|---|
| tier | AscensionTier | **书级单值**：本书所有条目同阶级。必非原生阶 |
| entries | list | **至少 1 条**；建议上限 8（仅 tooltip 折叠用，不强制） |
| entries[].enchantment | ResourceLocation | 原版附魔 id |
| entries[].level | int 1..255 | **语义 = tierLevel（曲线等级）**，不是存储等级 |

> **为什么 level 必须是 tierLevel**：存储等级升阶后永远是上限，把它 +1 得到的数字对强度毫无作用，
> 合并就变成空转。选 tierLevel，「两本同级书 → 升 1 级」才真的变强。

**实际生效值一律夹在该谱系该阶的 max_level 内**（逐谱系查，见 P1-28 的 StageLookup.maxLevelOf）：
耐久 3、保护 4、锋利 5。书里写 5、该阶上限 3 → 生效 3。

### 3.2 其余两类书（不变）

| 组件 | 科目 | 载荷 |
|---|---|---|
| ultraenchantment:ascension_spec | 进化型 | from_tier / to_tier / applicable |
| ultraenchantment:upgrade_spec | 升级型 | tier / target_level |

| 书 | 载荷 | 作用于装备 | 作用于载体书 | 成本 |

## 5. 铭刻书（载体书）逐条规则

### 5.1 贴到装备 · 生存模式（= 铭刻型升级书）

对每个条目独立判定：

| 条件 | 结果 |
|---|---|
| 装备上该谱系**无记录（原生阶）** | **拒绝** → 进剩菜 |
| 装备上该谱系阶级 == 书的 tier，且 entry.level > 当前 tierLevel | **生效**：tierLevel = min(entry.level, 该阶 max_level)；存储等级不动 |
| 装备上该谱系阶级 == 书的 tier，但 entry.level <= 当前 tierLevel | **拒绝** → 进剩菜（无变化） |
| 装备上该谱系阶级 != 书的 tier | **拒绝** → 进剩菜 |

> 等价说法：生存模式下它就是「升级书的附魔限定 + 多条目版」——不能凭空给装备上一个阶级。
> 想给白装备上高阶，必须走进阶书（原生→高阶）。

**一条都没生效 → 不产出**（输出槽为空，书不消耗，等于原版"无效操作"）。

### 5.2 贴到装备 · 创造模式（旁路）

| 差异 | 说明 |
|---|---|
| 放开「必须已有记录」 | 原生阶装备也接受：写入该谱系该 tier 的阶段条目，tierLevel = min(entry.level, 该阶 max_level)，**存储等级设为该阶 max_level** |
| 允许直接上究极 | ULTRA 载体书贴白装备 → 该谱系直接进究极阶（**跳过中间阶级**，这是刻意允许的调试能力） |
| 已有记录但阶级不同 | **仍拒绝**（防降级）【待确认 §9-6】 |
| 物品是否支持该附魔 | **不放开**：仍要求该物品 supportsEnchantment（照原版），否则锋利能刻到镐子上 |

> 旁路判据与现有实现一致：玩家 isCreative()，与进阶书的创造旁路同源。

### 5.3 剩菜（部分生效时的第二输出）

**定义**：本次**没有改变装备**的条目（被拒绝的 + 无变化的）。

**交付方式**：铁砧只有一个输出槽，无法原地留下第二件物品。因此：

1. AnvilUpdateEvent 阶段只设输出 = 装备（纯函数，两侧一致）；
2. AnvilRepairEvent（**服务端**，在槽位被清空前触发）用同样的输入重新解析一次，得到剩菜条目 → 重建一本载体书 → 进玩家背包；背包满则掉落。

| 剩菜书属性 | 值 |
|---|---|
| 阶级 | 与原书相同（转手不会改阶级） |
| 条目 | 只剩没吃下去的，level 原样 |
| 条目为 0 | 不交付（整本都被吃掉了） |

> 这是全模组**唯一**需要「第二输出」的操作。备选交付方式（把剩菜写回右槽）依赖菜单内部状态、且与清空槽位的顺序竞态，已否决。

### 5.4 书 + 书（铁砧合并）

| 情形 | 结果 |
|---|---|
| 同 tier | 条目**并集**；同一附魔：level 相等 → **+1**（夹该谱系该阶 max_level）；不相等 → **取 max** |
| 不同 tier | **拒绝**【待确认 §9-2：可选"低品质向高品质合并"】 |
| 互斥附魔（锋利 / 亡灵杀手） | 允许共存于书（与原版一致），贴到装备时才判 areCompatible |
| 结果为空 | 不产出 |

**这一条就是"同名合并升 1 级"在书层面的落地**（README §2 早就写了，一直没实现）。

### 5.5 转印（原版附魔书 → 载体书）—— 回答问题一

    原版附魔书 + 「基础→高阶」进阶书
      → 输出 ultraenchantment:advanced_enchanted_book
      → 载荷 { tier: ADVANCED, entries: [书上每条附魔 → level 1] }

| 规则 | 说明 |
|---|---|
| 门槛 | 每条附魔：原版书上的存储等级 ≥ min(目标阶 required_level, 原版 max_level)。锋利 → 必须有一本**锋利 V** 的原版书。**复用现成代码**（LineageTier.NATIVE 分支就是这么算的） |
| 条目 level | 一律 = **1**（曲线起点）。原版书上的 V 的价值体现在"够得上门槛"，与 v1 的「升阶后曲线归 1」同构 |
| 部分通过 | 默认【整本必须全部过门槛，否则不转】【待确认 §9-1】 |
| 产物 | 物品 id 变成我们的书（"是物品转变为进阶附魔书吗" → **是**） |
| 为什么必须有 | 生存模式下载体书不能贴白装备（§5.1），转印是**生存唯一获得载体书的渠道** |

## 6. 装备层同名合并（决定 4）

| 项 | 规则 |
|---|---|
| 触发 | 左槽与右槽是**同一物品**，且**两侧都有阶段记录** |
| 参与合并的谱系 | 两侧都存在、且**阶级相同**的谱系 |
| 同级（tierLevel 相等） | **+1**（夹该谱系该阶 max_level） |
| 不同级 | **取 max**（照原版）【待确认 §9-5：可选"只做同级 +1"】 |
| 阶级不同的谱系 | 不参与（不搬运、不取 max：避免靠吃掉一件高阶装备跳阶） |
| 其余一切 | **照原版**：耐久合并（含 12% 加成）、其他原版附魔合并、兼容性判定、先修惩罚 ×2+1、成本 |
| 其余情况 | 交回原版（非同名 / 任一侧无记录 → 行为完全不变） |

**代价（必须知情）**：这一条要求我们接管原版的合并数学——
即主动放开 AGENT.md **P1-13**「不在此重写原版的合并数学」的约定。
需要忠实搬进来：耐久合并公式、附魔合并循环（同级 +1 / 取 max / 夹 max_level）、
REPAIR_COST 的 calculateIncreasedRepairCost、成本累加。约 60~80 行 + 一个逐项对照原版的测试矩阵。

## 7. 成本表（v2）

| 操作 | 公式 | 例（锋利） |
|---|---|---|
| 进阶书（升阶） | 目标阶 anvil_cost | 3 / 5 / 7 |
| 升级书 | 固定 3 | 3 |
| 载体书 → 装备 | Σ max(1, anvil_cost/2) × 生效 tierLevel，最小 1【待确认 §9-7】 | 1 条 tierLevel 3 → 3 |
| 书 + 书 | Σ max(1, anvil_cost/2) × 结果 level + 先修惩罚 | 锋利 3+4 → 4 |
| 转印 | 进阶书的 anvil_cost | 3（基础→高阶） |
| 装备同名合并 | Σ 阶段 anvil_cost × 结果 tierLevel + 先修惩罚 ×2+1 | 高阶锋利 2+1 → 3×3=9 + 先修 |

> 一律**不低于 1**（cost == 0 → mayPickup 恒 false，输出拿不走，P0-5）。
> 被我们接管的操作**不会触发 40 级「过于昂贵」上限**（该分支在 setOutput 后被跳过）——这是既有行为，v2 不变。

## 8. 与原版铁砧的差异（v2 更新）

| 机制 | 原版 | 我们（接管时） |
|---|---|---|
| 等级上限 | 夹到 enchantment.getMaxLevel() | 不夹（写进去的本来就 ≤ 该阶 max_level） |
| 同名合并升 1 级 | 对**存储等级**生效 | 对 **tierLevel** 生效（§6） |
| 先修惩罚 | 每次合并 ×2+1 | 装备合并照原版；纯升阶 / 升级 / 载体书操作**不写**（永不涨价） |
| 40 级上限 | cost ≥ 40 → 输出清空 | 绕过，**永不触发** |
| 重命名 | +1 级，与操作同时生效 | 我们的分支**不读名称框 → 重命名被丢弃**（v2 未修，已知缺口） |
| 书 + 书 | 原版附魔书合并 | 我方书合并（§5.4）+ 原版书仍走原版 |
| 第二输出 | 无 | 剩菜书通过 AnvilRepairEvent 交付（§5.3） |
| 原版附魔书贴装备 | 正常 | **不变**（我们不接管，进阶状态不会跟着书走） |

### 12.4 实施顺序（建议）

1. 载荷多条目 + tooltip 多行 + 创造栏样本（先把契约立起来）
2. 贴装备（生存 / 创造分叉）
3. 剩菜（AnvilRepairEvent）

## 15. 提示框规格（从 README 移交，实现契约）

全部走翻译键 + 占位符，不用字面量拼接（专用服务器没有语言数据，P1-17）。

**通用约定**：标题行金色 · 标签行暗灰 · 附魔行与阶级名行用普通附魔同色（GRAY）·
阶级配色 高阶 = 蓝 / 超级 = 淡紫 / 究极 = 金，与附魔行上的阶级色一致。

### 15.1 进化型 · 通用进阶

    h1  附魔进阶
    h2  可应用于附魔：
    h3  普通附魔 / 高阶附魔 / 超级附魔
    h4  进阶为：
    h5  高阶附魔 / 超级附魔 / 究极附魔

| 品质 | h3 | h5 |
|---|---|---|
| 基础→高阶 | 普通附魔 | 高阶附魔 |
| 高阶→超级 | 高阶附魔 | 超级附魔 |
| 超级→究极 | 超级附魔 | 究极附魔 |

通用进阶不写具体附魔名，只写阶级范围。

### 15.2 进化型 · 定向进阶

**h3 写「上一阶」，不是原版附魔名。** 定向书是「限定谱系的通用进阶书」，
描述的同样是链上的一条边：

- `h3`（可应用于附魔）= `from_tier` 那一阶的名称；只有 `from_tier` 是原生阶时，
  「上一阶」才恰好就是原版附魔本身。
- `h5`（进阶为）= `to_tier` 那一阶的名称。

| 品质 | h3 | h5 |
|---|---|---|
| 基础→高阶 | 锋利（原生阶退原版附魔名） | 高阶锋利 |
| 高阶→超级 | 高阶锋利 | 超级锋利 |
| 超级→究极 | 超级锋利 | 究极锋利 |

（早期实现把 h3 一律写成原版附魔名，读起来像「原生锋利直接推到超级」，规格与实现均已更正——见 AGENT.md P1-30。）

### 15.3 铭刻型 = 载体书

    h1     高阶附魔
    h2..hN 高阶锋利 IV
           高阶抢夺 III        ← 每条目一行，多条目书就是多行

- `h1` = 阶级名 + 「附魔」；
- `h2..hN` = 该阶级附魔的**独立本地化名**（`高阶锋利`，不是「阶级词缀 + 原版名」拼的）+ 曲线等级；
- 等级省略规则照原版：**1 级且该阶级上限为 1** 才省略数字（见 P1-32）；
  判定与物品上的进阶附魔行**共用一份实现** `StageLookup.displayLevelCap`。

### 15.4 升级型

    h1  高阶升级 III
    h2  可应用于附魔：
    h3  高阶附魔

`h1` 中的罗马数字 = 本书可把附魔提升到该等级。**这里不套用 §15.6 的省略规则**——
它描述的是「本书的效力」，不是某个附魔当前的等级，所以恒显示。

### 15.5 祛咒石

    h1  可应用于：
    h2  高阶附魔 / 超级附魔 / 究极附魔

结构与升级书的前两行同源（同一套 `applies_to` / `tier_scope` 键）。

### 15.6 物品上的进阶附魔行

    Advanced Sharpness III      ← 阶级附魔名 + 曲线等级
    Advanced Mending            ← 该阶级上限为 1 的谱系：省略数字

| 项 | 规则 |
|---|---|
| 名字 | 阶段条目自己的键 `enchantment.ultraenchantment.<阶级>.<附魔>`，与书 h2 同源（整合包可覆盖重命名） |
| 数字 | 显示 **`tierLevel`（进阶曲线等级）**，不是物品上存储的附魔等级（存储等级只留给原版机制读） |
| 省略 | 与书 h2 **完全同一条**：`level != 1 \|\| cap != 1` 才显示数字；`cap` = 该阶级阶段条目的 `max_level`（逐谱系，P1-28），查不到退化为原版附魔自身上限 |
| 实现 | `StageLookup.displayLevelCap`——**只准有一份**。v2.6 之前物品这条路漏了这条规则，5 条上限=1 的谱系全被写成「高阶经验修补 I」（见 AGENT.md P1-32 补记） |
| 受影响谱系 | 经验修补 / 引雷 / 火矢 / 无限 / 多重射击（数据包里 15 个格子 `cap == 1`） |

**攻击伤害的口径（v2.13 决定）**：进阶物品**不额外插「加成行」**，tooltip 保持
「阶级附魔行 + 原版属性段」的原样。

原因是两条口径本来就不同：原版属性段只统计 `ATTRIBUTES` 组件（不含附魔的 `DAMAGE` 效果），
第三方提示框又只按**存储附魔**套原版公式——实测下界合金剑三个样本（裸 / 原版锋利 V / 阶级究极锋利 V）
的属性行**全是 7**，而真实附魔加伤是 **0 / 3 / 20**。

v2.12 曾试过自己插一行真实增量，**作者要求保持原样，已在 v2.13 完整撤销**。
现象解释与「不要再插行」的提醒留在 AGENT.md P1-39。

## 17. v2.2 修正：两条实机 bug 与三处加固

### 17.1 「进阶书 / 升级书推不动载体书」

- **症状**：拿进阶书（通用或定向）去点一本载体书，毫无反应。
- **真因**：分派顺序。v2.0 写成「两本都是我们的书 → 走合并」，而合并只认
  「载体书 + 载体书」与「升级书 + 升级书」——**「拿书去推一本书」这条规格 §4 里写明的路被整条吞掉**。
- **修法**：两本都是我们的书时，先试 `applyBookAdvance`，返回 false 才落到合并。
  - 进阶书 → 整本书阶级 +1，所有条目曲线等级归 1；成本取目标阶 `anvil_cost`（多条目取最大）。
  - 升级书 → 所有条目曲线等级提到目标值（逐条夹取），成本 3。
  - **定向进阶书遇到多条目书里混了别的附魔 → 整本拒绝**（书的阶级是书级单值，拆不开），提示玩家改用通用书。
  - 门槛与装备侧同源：每条目都要 ≥ `min(目标阶 required_level, 来源阶上限)`；创造旁路跳过。
- **至此双宿主（装备 / 载体书）在「升阶、提级」两条规则上完全对称。**

### 17.2 「创造模式用高阶段的书贴物品导致失去世界连接」

- **真因（按可能性最高的机制处理）**：铁砧的处理入口跑在**容器包处理链**里，
  任何未捕获异常 = 服务端线程中断 = 客户端「失去世界连接」；
  另一条同类路径是**写入越界值**（附魔等级超出可序列化范围）→ **网络编码阶段**炸，同样是掉线。
- **修法（三处加固）**：
  1. `AnvilEvents.onAnvilUpdate` 整体兜底：异常降级为「本次不产出」+ 错误日志；
  2. `AnvilTakeEvents.onAnvilRepair` 同样兜底（剩菜书交付失败也不许掀线程）；
  3. 写存储等级前一律夹进 `min(该阶上限, 该附魔原版上限, 255)`。
- **复现尝试（未成功，已留档）**：90 个阶段条目（30 谱系 × 3 阶级）各造一件产物，
  做 **网络编码 → 解码往返**（当时 93 次）与**结算 + 单点查询 + tooltip**；
  另对创造旁路直接解析 90 例（全谱系）。**零异常、零编码失败**——数据与逻辑侧不可复现。
  因此本次按「包处理链异常」堵死：今后再有此类问题，日志里会留下
  `Anvil handling failed` / `Leftover book delivery failed` 与完整栈，而不是玩家直接掉线。

### 17.3 顺带修掉的一处架构缺陷（**不是**本次掉线的成因）

拿到更精确的现象后（**在铁砧上放入物品 + 高阶附魔书，一放上去就掉线**），复查出并修掉了一处
**依赖方向错误**（v2.0 引入，我自己的）：

| 项 | 内容 |
|---|---|
| 现场 | 运行期的 `logic/BookFactory`（铁砧产物造书）调用 `datagen/UEModels.predicateOf(...)` |
| 为何致命 | `UEModels extends ItemModelProvider` —— **客户端**模型生成器 API。只跑服务端的发行版里加载它会抛 `NoClassDefFoundError`；而该调用就在铁砧结果槽的写入路径上（包处理链），所以表现是玩家直接掉线 |
| 为何 dev 复现不出 | 开发环境客户端/服务端类同处一个 classpath，147 例（物品 × 进阶书 / 升级书）全组合零异常 |
| 修法 | 编码算术下沉到运行期 `content/BookView`，**datagen 反过来调运行期**；模型 JSON 逐字未变（已 diff 验证），147 例仍全绿 |
| 防复发 | AGENT.md 新增 **P0-16**（运行期包不得 import datagen / 客户端类）并写进 §6 提交前清单 |

> **但本条不是这次掉线的成因**——它是一处真实、该修的缺陷，属顺带加固。真正成因见下。

## 17.4 掉线的真正成因：注册表**侧别**错配（v2.4）

工作区里的客户端日志（`run/logs` 的轮转归档）给出了决定性证据：

    Internal Exception: io.netty.handler.codec.EncoderException:
        Failed to encode packet 'serverbound/minecraft:container_click'
    Caused by: java.lang.IllegalArgumentException:
        Can't find id for 'Reference{ResourceKey[minecraft:enchantment / minecraft:smite]=Enchantment 亡灵杀手}'
        in map net.minecraft.core.Registry$1@...
        at net.minecraft.core.IdMap.getIdOrThrow
        at net.minecraft.network.codec.ByteBufCodecs$25.encode          // holderRegistry
        at net.minecraft.core.component.DataComponentPatch.encodeComponent

| 项 | 内容 |
|---|---|
| 现象 | **单机（集成服务器）+ 创造模式**：物品 + 高阶附魔书放进铁砧 → 立刻掉线 |
| 失败点 | 客户端要发出的 `serverbound/container_click`（装着客户端本地生成的铁砧结果栈） |
| 机制 | `ByteBufCodecs.registry(...)` 用 `IdMap.getIdOrThrow(holder)` **按值查 ID**；服务端与客户端的 `Enchantment` 是两套不同实例（record 内嵌各自那一侧的 HolderSet / 效果组件），跨侧不相等 → 查不到 ID → 编码失败 → 连接关闭 |
| 为何会跨侧 | `CommonHooks.resolveLookup` 的第一优先级是 `ServerLifecycleHooks.getCurrentServer()`；**单机的集成服务器一直存在**，于是**客户端线程**上它也返回**服务端**注册表。而创造旁路「白装备直上阶级」会把 `enchants.get(...)` 拿到的 Holder **写进物品的附魔组件** |
| 为何此前测不到 | 专用服务器两侧同一张表；纯多人客户端没有集成服务器（回落客户端表）。**只有「单机 + 客户端本地生成栈」**这一种组合会炸 |
| 修法 | 新增 `logic/UELookups.enchantmentsForItemWrites(clientSide)`：逻辑客户端用 `ClientHooks.resolveLookup`，否则用 `CommonHooks.resolveLookup`；铁砧分派与取件改走它 |
| 关键细节 | 集成服务器**两侧线程同时在跑**，判据必须是 `level.isClientSide()`，**不能**用 `FMLEnvironment.dist`（否则服务端线程会错用客户端表） |
| 配套守卫 | 写入前检查 `holder.unwrapKey().isPresent()`，把运行时组装的合成 Holder（P0-2）挡在门外 |

## 18. JEI 兼容（v2.5）

### 18.1 问题：单例物品 + 组件变体，在 JEI 里会塌成一条

书与祛咒石都是**单例物品**（几百个变体共用同一个 `Item`，只靠组件区分），
而 JEI 判断「同一种材料」用的是 **subtype**，**默认不认数据组件**。

**实测证据**（同一份代码、同一个存档，只切换「注册 / 不注册」；数字来自
`UEJeiPlugin.onRuntimeAvailable` 里的 `[JEI]` 日志）：

| 场景 | 进阶附魔书 | 祛咒石 |
|---|---|---|
| 不注册（JEI 默认） | **1** 条 | **1** 条 |
| 注册 subtype | **384** 条（进化 93 / 载体 276 / 升级 15） | **3** 条 |
| 注册 subtype（v2.7 纳入穿刺后） | **402** 条（进化 96 / 载体 291 / 升级 15） | **3** 条 |

原版附魔书能逐本列出，是因为 JEI 的原版插件内建注册了同类解释器。

### 18.2 实现

`compat/jei/UEJeiPlugin`（`@JeiPlugin`，`IModPlugin`）：

- `registerItemSubtypes` 给书与祛咒石各注册一个 `ISubtypeInterpreter<ItemStack>`；
- 键 = **语义载荷**（载荷组件经自身 codec 转 JSON），而不是整份组件：
  修复费 / 自定义名字 / 耐久等无关数据不会把同一变体分裂成多条；
- `onRuntimeAvailable` 打一行 `[JEI] 材料表：…`（**可失败的检查**：
  把注册注释掉，条数会塌回 1）。

### 18.3 版本与依赖

| 项 | 取值 |
|---|---|
| 开发依赖 | `mezz.jei:jei-1.21.1-common-api` + `neoforge-api`（`compileOnly`）、`jei-1.21.1-neoforge`（`runtimeOnly`）；**不进 jar** |
| 接口选择 | `ISubtypeInterpreter`（新）；`IIngredientSubtypeInterpreter` / `NONE` 已过时待删 |
| 兼容实测 | JEI **19.44.0.400**（用户实例）与 **19.57.0.450**（开发依赖）接口一致 |
| 服务端安全 | `@JeiPlugin` 由 JEI 自己扫描；插件类只在装了 JEI 的客户端被加载（P0-16） |

### 18.4 铁砧配方页（v2.9 重做）

一个 JEI 类别「**附魔铁砧**」（`compat/jei/AnvilRecipeCategory`），三类操作，配方上那行字就是类别：

    附魔进阶   [物品] + [进阶书]  →  [进阶后的物品]
    附魔合并   [书]   + [书]      →  [合并 / 推阶 / 提升 / 转印后的书]
    附魔升级   [物品] + [升级书]  →  [等级更高的物品]

**轮播**：三个槽都吃列表（`addItemStacks`），JEI 会在同一格里轮播——「中间等级」靠它展示：
一条配方覆盖 2..上限 的全部升级书与对应结果，条目数不膨胀。

**进阶要求**（悬停左槽或整条配方可见）：文案按机制本身给，**哪个适用就显示哪个**——
门槛恰等于源阶段上限时写「达到满级（N 级）」，否则写「达到 N 级（该阶级上限 M 级）」。
判据与 `AscensionLogic` 同源：`min(目标阶 required_level, 源阶段上限)`，
原生阶比**存储等级**、已进阶比**曲线等级**；左槽展示的正是**刚好够门槛**的那个等级。

**类别图标**：三本书（进阶 / 载体 / 升级）**轮播**——自实现 `IDrawable`，按秒切换。

**内容与规模**（**v3.0 实测 `[JEI] 附魔铁砧配方 170 条`**；v2.9 为 286 条）：

| 类别 | 条数 | 内容 |
|---|---|---|
| 附魔进阶 | **59**（v2.9：93） | 每条谱系 × 其真实的每个阶级一条（左槽 = 刚好够门槛的等级；**v3 起门槛 = 满级**） |
| 附魔合并 | **65**（v2.9：115） | 载体书 + 载体书（每阶级 1 条，样本取「能贴到同一件物品上」的一对）、载体书 + 进阶书（原为 62）、载体书 + 升级书（原为 16，只在真能提升时产出）、原版附魔书 + 进阶书转印（原为 31）、升级书 + 升级书（每阶级 1 条）。**v3 后各分项需重新插桩统计**（当前日志只打三个大类） |
| 附魔升级 | **46**（v2.9：78） | 有可提升等级的格子（该阶级上限 ≥ 2），书与结果轮播 2..上限 |

- **结果一律调用铁砧那套纯函数**（`InscriptionLogic.mergeBooks / advanceTier / upgradeEntries / transcribe`）算出来，
  不手写近似值——逻辑改了这里跟着变；
- 催化剂 = 铁砧（三种状态）+ 进阶附魔书 + 祛咒石；
- 展示用 `ItemStack` 由客户端构造，取附魔 Holder **必须**走
  `UELookups.enchantmentsForItemWrites(true)`——否则单机上会拿到服务端 Holder（**P0-17**）；

  把每条配方里的每个展示栈都真的编码一遍。

## 20. v2.8：创造栏回归「只放单条目载体书」

### 20.1 纠正什么

v2.7 往搜索标签投了 3 条**多条目**载体书样本（每阶级一条），想用它展示「载体书可以刻多条」。
作者指出：**这本身就违约**——最初定夺的创造栏投放规格只有「谱系 × 阶级 × 等级」这**一条单条目轴**。

v2.7 的修法（把样本换成「条目能贴到同一件物品上」的组合）**方向错了**：问题不在取样规则，
而在「创造栏不该有多条目书」这件事本身。多条目书与单条目书**共用同一套材质**
（外观只有「科目 × 阶级」两个维度），摆在列表里读起来就是「某条附魔的书莫名多了一条别的附魔」，
界面上没有任何东西能说明它是刻意的样本——玩家只能理解为数据乱了。

### 20.2 现在的规矩

| 来源 | 允许的条目数 |
|---|---|
| 创造栏（主标签 + 搜索标签） | **只放单条目书**（谱系 × 阶级 × 等级） |
| 玩家在铁砧上合并两本载体书 | 可以刻多条（规格 §5.4，玩法能力） |
| 转印（原版附魔书 + 进阶书） | 单条目（那本书只有一条附魔） |

### 20.3 校验（可失败）

`UEJeiPlugin.checkNoMultiEntryBooks`：客户端启动后遍历材料表，
**发现任何多条目载体书就报 ERROR** 并列出阶级与条目；约定值 **0**。

实机实测（v2.8）：

    [JEI] 材料表：进阶附魔书 399 条（进化 96 / 载体 288 / 升级 15），祛咒石 3 条
    [JEI] 创造栏多条目载体书 0 本（约定值 0）

实机实测（**v3.0**，阶段 93 → 59 之后）：

    [JEI] 附魔铁砧配方 170 条（附魔进阶 59 / 附魔合并 65 / 附魔升级 46）
    [JEI] 材料表：进阶附魔书 258 条（进化 62 / 载体 181 / 升级 15 / 空白 0），祛咒石 3 条
    [JEI] 创造栏多条目载体书 0 本（约定值 0）
    [JEI] 配方展示栈编码校验：662 个栈，失败 0 个（约定 0）

### 22.3 对账中修掉的一类**静默翻倍**（必读）

老式 `value(...)` 是「能合就合、否则追加」。当原版那条**带条件**（亡灵杀手「仅亡灵」、穿刺「仅水生」）
或已被阶级曲线改写时合并不上 → 原版条与我们那条**同时存在**，数值翻倍。
v3 新增**绝对覆盖**原语 `absoluteValue(...)`：有原版条目则**沿用其 conditions**、只换数值；没有则新建。
实测并修复：穿刺、力量、穿透、抢夺、击退、饵钓、海之眷顾、多重射击、爆炸保护超级（残留缩放值）。

> 「故意保留两条」的四处：火矢（原版点燃 100 + 额外 60）、火焰附加究极（额外点燃叠两层）、
> 效率究极（两条额外挖掘效率）、激流三阶（原版三条音效）。

### 22.4 荆棘（唯一必须改写原版条目的谱系）

反伤范围 / 耐久消耗 / 触发概率都不是「新增一条」能表达的：

- 反伤的 `damageType` 是 `Holder<DamageType>` → **不能**自己造 `Holder.direct`（P0-2），只能沿用原版那条；
- 概率条件的实际结构（运行期实测）：`LootItemRandomChanceCondition(EnchantmentLevelProvider(Linear(0.15, 0.15)))`
  ——按附魔等级算概率，必须原样保留。

因此 `UEStageEffects.thorns(...)` 走 `Rewrite`：取出原版 `post_attack` 第 0 条，
沿用它的 `enchanted/affected` 与伤害类型，重建 `AllOf(DamageEntity(min,max), DamageItem(amount))`
与概率条件。三阶实测：`2~10/耐久2/0.30`、`4~20/耐久1/0.45`、`8~40/耐久0/0.60`；
**不再挂** `damage_protection` 与 `knockback`。

## 23. v3.1：对外 API 契约

**面向模组作者的完整文档**：[api.md](api.md)。本节只记录**契约要点**与实现落点。

### 23.1 公开面

`com.lyingice.ultraenchantment.api` 包（其余包不保证兼容）：

| 类型 | 内容 |
|---|---|
| `UltraEnchantmentApi` | 查询：`getTierLevel` / `getCurveLevel` / `isUltraEnchant` / `getMaxAllowedTier` / `isEnchantLocked` / `getStageId` / `getImcAttribute`；修改：`setTierLevel` / `setCurveLevel` / `unlockEnchant` / `removeUltraEnchant` |
| `api.event.UltraEnchantTierUpgradeEvent` | 可取消；`source` = ANVIL_BOOK / UPGRADE_BOOK / MERGE / API |
| `api.event.UltraEnchantLockChangeEvent` | **不可取消**（解锁已扣祛咒石耐久，取消会造成不一致） |
| `api.UltraEnchantImc` | 三通道：`register_enchant` / `tier_attributes` / `upgrade_cost`，载荷 String |

### 23.2 两个「等级」的对外命名（**必读**）

| 概念 | 内部叫法 | 对外叫法 | 取值 |
|---|---|---|---|
| 阶级 | `stage`（`LineageTier`） | `tier` | 0=原生 1=高阶 2=超级 3=究极 |
| 该阶曲线等级 | `tierLevel`（组件字段 `tier_level`） | `curveLevel` | 1..该阶上限 |

内部字段名**不改**（已进存档与网络格式），公开层做映射。效果强度按 `curveLevel` 结算。

### 23.3 行为约定

- 查询双端可用、无副作用；未进阶/不支持一律返回 `0`，不抛异常；
- 修改**只在逻辑服务端主线程**生效，否则 `false` + WARN；
- `setTierLevel` 越界**不夹取**（拒绝），`setCurveLevel` 夹取 + WARN（与升级书一致）；
- `setTierLevel(tier==0)` 等价 `unlockEnchant`；升阶时 `curveLevel` 归 1；
- 事件取消 = **整次操作作废**（不落盘、不扣材料）；所有写入路径统一经 `logic/UEEvents` 发事件。

### 23.4 落点（实现）

| 文件 | 职责 |
|---|---|
| `api/UltraEnchantmentApi.java` | 门面：校验 → 发事件 → 写组件 |
| `api/event/*.java` | 两个事件（纯数据，无内部依赖） |
| `api/UltraEnchantImc.java` | 通道名与键名常量 |
| `logic/UERoots.java` | 「附魔 → 谱系根源」**唯一实现**（合成附魔走 `EnchantmentFactory.rootOf`，普通走注册表；客户端退回 side-aware lookup）。dummy 兼容补丁已改为调用它 |
| `logic/UEEnchantRegistry.java` | IMC 调参表（上限收紧 / 自定义键值 / 升级花费），**与数据包分开存**、查询时合并 |
| `logic/UEEvents.java` | 事件唯一发射点 |

`runServer` 自检 **43 项断言全绿**：查询（含「财富/忠诚 不支持」「保护上限=1」）、写入、
越界拒绝、**事件取消后零副作用**、IMC 合法/坏格式/越界值/收紧后 API 可见。
